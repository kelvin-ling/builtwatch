# October 18: backend maps with review pins

## What changed

- **Backend map per app.** A profile may carry an optional `architecture`: components
  (entry point, service, data store, AI model, outside service) and the data flows between
  them. The map replaces the four-step flow everywhere it appeared:
  - Profile dialog: the full map, the reviews that land on it, and "what to check" for each.
  - System cards: only the hit components and their neighbours, plus a link to the full map.
  - Review dialog: the one review in focus, the components it hits, everything else dimmed.
- **Placement is exact, not inferred.** A review lands on a component when the profile fact
  it matched (`services[i]`, `technologies[i]`, `data_categories[i]`,
  `consequential_actions[i]`) is listed in that component's `uses`, `data` or `actions`.
  Reviews that cite only whole-app facts (purpose, rules, regions) are listed as whole-app.
  Components connected by a flow to a hit component are flagged "check next".
- **Who analyses the backend.** The user's own project agent, from a copied request
  ("Map backend with agent"). It reads the code locally; BuiltWatch receives only the
  component map, validates it, previews it, and saves it with the profile. BuiltWatch still
  never reads app code, connects to the app, or accepts a URL from a profile (invariant 7).
- **Grounded.** The server rejects a map whose components cite a dependency, data
  category or action the profile does not record. When a pasted map introduces one, the
  dialog shows it and adds it to the profile on save, so the daily check watches it.
- **Monitoring is unchanged.** The daily rules check still matches source changes against
  recorded dependencies; the map decides where the match is drawn. No new route, fetch,
  model call or scheduled job was added. Profiles remain under the 24 KB request limit.
- Demo: Client Inbox Triage Bot and Website Support Chat Widget carry agent-style maps; the
  Static Recipe Archive shows the derived map until a map is pasted.
- Removed the four-step flow map (`flowMap`, `BuiltWatchPerspectives.flow`) and its CSS.

## Cost

This feature adds no AWS service, route, fetch, scheduled job or model call. A saved map
makes a profile item a few KB larger in DynamoDB; request counts are unchanged.
BuiltWatch's own AWS usage in rules mode is roughly USD 0.05–0.10 per month before
credits (DynamoDB requests and S3 storage; Lambda, Cognito and CloudWatch within free
tier). Website hosting is billed separately.

## Follow-up (18 October, later)

- Saved maps survive profile updates that do not resend them: a connected agent's sync,
  edits and bulk imports keep the saved map (trimmed to facts still recorded). A missing
  and a null map both mean "not resent"; removal is explicit (`remove_architecture`, the
  dialog's **Remove map**).
- Review cards say where a change lands: "Lands on Shared client inbox, Outbound email
  (SendGrid) · check next: Triage function". The agent handoff prompt and Markdown digest
  carry the same placement, so an investigating agent starts in the right component.
- Bulk import checks any included map before submit, naming the first ungrounded entry.
- Fixed: overview cards after the first showed the change headline instead of the app
  name (`map(findingRow)` passed the array index as the grouped-view flag).

## Hourly improvements

- Fixed a false "map is stale" warning: pasting an agent analysis dated days earlier
  updated the profile in the same save, so the warning fired at once. The server now
  stamps `architecture.recorded_at` whenever a request supplies a map (web save, bulk,
  agent sync), and staleness is judged from that. Profile edits no longer resend the map,
  so they keep its save time; the demo keeps maps the same way the server does.
- **By when.** Take-effect dates are read from each review's quoted source text, only
  where requirement wording sits right before the date ("Starting February 1, 2024",
  "by March 1, 2027", "will be removed on …"); publication and labelled page dates are
  ignored. The exact phrase is always shown with the date. Dates appear on review cards,
  in the review dialog ("When it takes effect"), in backend-map landings, in the agent
  handoff and the digest, and in an Overview "By when" timeline (soonest first, then
  dates that already passed), each saying which component the change lands on.
- **Add to calendar.** The Overview "By when" panel offers a `.ics` file of every upcoming
  take-effect date in open reviews: one all-day event per review, carrying the exact quoted
  phrase, the source, and the backend component it lands on. Dates that already passed are
  left out, and the button only appears when an upcoming date exists. The file is built in
  the browser; nothing is sent anywhere.
