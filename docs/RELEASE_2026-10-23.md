# Faster, consistent Impact totals and specific review headings — 23 October 2026

Backend only (AWS functions). No website, model, schedule, quota, storage schema or
service configuration changes.

## Public Impact totals

Recomputing the anonymous totals read every record in every workspace partition,
including the full page snapshot each daily check stores per source. A visit after the
fifteen-minute cache expired waited 5–7 seconds, and a direct link to `#impact` showed
"Loading your watch desk…" for that long. The wait grew every day and would eventually
pass the gateway's 15-second limit. The recompute now reads only app, check, review and
outcome records, several workspaces at a time.

"Systems currently need review" counted every relevant finding without a decision,
including ones each workspace already hides: findings from superseded matching rules,
older revisions of the same change, matches the current rules withhold, and reviews of
apps that were removed. It now uses the same filter as the workspace (`shown_reviews`),
so the public count matches what owners see on their desks. Other totals are unchanged.

API cold starts no longer import the scan pipeline and its agent SDK; only the scan task
loads them (local import time of the API handler 532 ms → 204 ms).

## Review headings

Rule matches were all titled "Review a source change connected to <dependency>". New
matches are titled from the quoted passage's own words: the kind of change (security
issue, deprecation or removal, breaking change, migration, new requirement, pricing,
limit, or simply change), the recorded dependency, and the take-effect date when the
source records one or the passage states exactly one, for example
"New requirement · Gmail API · effective Feb 1, 2024". Stored matches with the old
heading are retitled when read; stored records, dedup identity and outcomes are untouched.

The server reads dates with `src/builtwatch/deadlines.py`, the twin of
`web/deadlines.js`. Both are tested against `tests/fixtures/take_effect_cases.json`.

Validation: Ruff, 260 Python tests (one skip), 103 JavaScript tests, syntax and build
checks, and the zero-model rules benchmark (31/31). New tests fail on the previous code:
126 items read instead of 5 for a workspace with 60 days of snapshots, 4 systems needing
review instead of 1, and the pipeline loaded by the API handler. The live website was
rendered against a local workspace response to check the new headings at 1280 and 390
px. Rollback: redeploy the backed-up packages from this release's backup folder.

## Later on 23 October: Impact answers at once; faster workspace loads

Backend only, again. No website, model, schedule, quota, storage schema or permission
changes. The API function already had permission to invoke the worker.

**Impact never waits on a recompute.** After the fifteen-minute cache expired, the next
visitor still waited while every workspace was re-read (about 5 s cold on the live page).
Saved totals are now answered at once, with their own "Updated" time. The first visitor
to reach stale totals claims one background refresh (a conditional write on
`GLOBAL#impact`, which can be claimed again after 5 minutes if it never finished), and
the worker recomputes the totals (`{"task": "impact"}`). Each finished check also
refreshes them, so the page moves when the daily checks complete instead of up to 15
minutes later. Totals more than a day past expiry, or a table with none saved, are still
computed inline. A failed refresh request is logged and the saved totals still answer.

**Workspace loads.** Deciding which rule matches to show resolved each declared product's
names again for every passage of every review: 84% of that step. That result is now
memoized per name. A full workspace (10 apps, 300 reviews) filters in 22 ms instead of
80 ms locally.

Validation: Ruff, 273 Python tests (one skip), 103 JavaScript tests, syntax and build
checks, and the zero-model rules benchmark. The 13 new tests fail on the previous code.
